# 潜力1.1：60%步数分组返航、分级交互与择图提交——代码修改完整设计

版本：设计稿 v1.0；日期：2026-11-21。

**本文件是待实施方案，不是已完成的代码或测试报告。本轮未修改算法、未运行新仿真。** 已有比赛结果仅用于解释设计依据；下文参数和验收用例均需在实施后验证。

## 1. 最终要实现什么

达到最大步数的60%后，已完成自身投弹的无人机结束主动远探索，沿已走过的安全通道返回。交互位置来自出发后的实际分开区域，不强制回出生点，也不强制围绕0号机。

采用“组内先汇合、组间再交换”的结构：例如前三架在A点交换，后两架在B点交换，两组各选携图者到共同约定的C区域交换。最终比较各机保留的候选图和可选融合图，持有最佳候选图的无人机负责提交。图的原作者、携图者、提交者可以是不同无人机。

需要保留三个现实边界：

- 3+2是可能出现的队形，不预先写死成员。实际若分成4+1或2+2+1，按实际分支归组；没有可靠组信息的机器先视为单机组。
- C点必须双方已经知道且有已知可达路线。断联后各算一个几何中点，会造成两组到不同地方等待。首版优先采用共同分开区域或共同父通道，C可以与A或B重合。
- 在线无法获得官方真实地图分。“选最高分”只能实现为统一证据下的质量估计，不能承诺一定选中官方评分最高的图。官方分用于赛后对照。

**60%是启动返航的门槛，不是强制提交时刻。** 保留现有投放复核，不在仍有未确认炸弹时伪造“全队完成”。未投完的机器继续原有投放流程，完成后加入交互或直接赶往C。

## 4. 会合点怎么记录、怎么选择

### 4.1 从“满足全队几何阈值”改为“记录真实接触与分支历史”

探索期间只做轻量记录，不改变导航。每次真实收到直接邻机消息，记录接触双方、时刻、各自估计位置与可靠性、所在历史路径索引。转发消息中的第三方位置只能作提示，不能冒充本机与第三方发生直接接触。

各机保留沿途关键路径节点及相邻通道，优先复用旧返航模块中路径压缩、回环裁剪和已知通道检查的可用部分。保留既有安全净空规则，不为通过测试降低机身碰撞要求。

短暂丢一帧不判定为分开。可把连续40步没有直接接触作为“分支稳定”的初始设计值；它只决定记录何时成熟，不成为拒绝所有候选点的硬门槛。定位欠佳时仍保留接触事件，但不把不可靠坐标直接选为精确返航目标。

删除旧版“所有飞机必须距0号不超过150 px”要求。也不再叠加“全队跨度160 px”和“离起点140 px”作为唯一入口。是否属于出发后的分开区域，由接触序列和路径分叉判断；优先选择离开初始停机区域后的通道节点，没有有效节点则不启动新返航任务。

### 4.2 A、B、C分别代表什么

| 区域 | 选择依据 | 执行方式 |
|---|---|---|
| A：较早分开组的局部交互区 | 该组成员最后共同经过、实际能通信的分支附近 | 组员各沿自己的历史路径返回，在能真实收包时立即交换 |
| B：另一分支末两架分开的局部交互区 | 两架最后实际接触的共同通道；不是单纯最后靠近的位置 | 两架先交换，选一架携图；若该处已不可用则回退共同父通道 |
| C：组间交互区 | 两组已共同确认的父通道或已约定的可达接触区域 | 携图者交换；途中提前接触即可完成，不要求必须走到一个像素点 |

会合点采用“通道区域+路径入口”，不要求5个机身中心重合。是否完成通信以真实收包和版本确认判断；不再发明一个围绕0号机的全队距离限制。

选择同组候选点时，按已知通道长度估算到达时间，优先最小化该组最慢成员的预计到达步数，再比较总路程。C只在双方已有共同认知的可达候选中比较，不穿墙取直线中点，不使用真实全图导航。

### 4.3 解决“断联后双方算出不同C点”

首版必须先建立一个共享的父交互区 `root_region`，再允许组内局部优化：

1. 临时标记发布者只负责发布元数据，可用固定编号顺序确定，避免多机同时提出互不兼容的根点。这个角色不等于收图者或提交者。
2. 发布 `epoch、plan_version、root_region、各机历史路径入口`。各机只有确认自己知道该区域且有已知路径后才ACK；允许多跳、分时传播，不要求5机同一帧在一起。
3. 每架对同一epoch只接受一个当前根点版本。ACK表示接受该共同目标，以及60%后至协同期截止前的普通提交协调约定；不是地图已收齐的证明。
4. 收齐5个实际ACK，才可在日志中宣称“全队共同返航计划已建立”。证书通过原有接触传播。根点一旦进入执行期就冻结，不在断联期间追随未确认的新坐标。
5. A/B可由各组后续接触历史细化；C默认仍为共享父区。只有两组真实交换并确认新版本后，才允许把C缩短到新的共同通道。

根点提议应在离开初始区域后、队伍尚有实际接触链时提前发布，例如取正在经过的共同通道节点；不能等“最后两架也已经断联”才第一次发布。这里不再要求达到某个全队跨度。后续首次分开和最后两架分开的记录用于细化A/B，已经传播的父节点承担C的共同后备区域。

这套小元数据确认不是让5架先返回交互一次。它在探索期间搭车传播。若探索期间始终无法形成共享根点，首版应明确记录 `no_shared_root`，保持原算法，不为了“必须会合”清空旧任务。

未知组关系的机器按单机组返回共享根点。不得根据远端过期坐标凭空假定固定3+2分组。根点有效但局部A/B缺失时，直接使用根点；根点本身无效时，新策略不接管。

## 5. 返航门槛、任务接管与退出

### 5.1 唯一返航触发门槛

```python
return_start = limit * 3 // 5
ready = (
    step >= return_start
    and actual_own_inventory == 0
    and pending_drop is None
    and not placement_escape_active
    and valid_accepted_plan
    and known_return_route_available
    and coordination_budget_available
)
```

`actual_own_inventory`沿用原版实际库存同步，不用已发投弹指令代替。投放后正在脱离或末弹尚未确认时，返航不得抢占控制。以5400步为例，最早3240步开始；1号若4027步才确认末弹，不能要求它3240步完成交互。

### 5.2 先预检，再接管

新增 `prepare_return()` 只读检查，返回不可变的 `ReturnIntent` 或失败原因。它不清空路线、不修改 `search_task`、不结束旧信使。

只有取得有效Intent，才执行 `commit_return()`：记录原任务交接、去掉旧信使导航所有权、安装返航目标、进入新状态。同一epoch只接管一次；重复广播、重复ACK和局部组成员刷新不重置计时器，不重建往返任务。

未形成计划、无路可走或预算不足时，必须保持原命令和原任务状态。这个要求用完整状态快照反例验证，不能只检查返回值。

接管后遇动态障碍，仍由既有驱动和避障处理。若通道失效且既有寻路也不能找到已知安全替代路径，退出新任务并回到原版流程；不能用不可靠坐标硬冲墙，也不能无限停在障碍前。

返航目标不再作为普通探索目标交给 `SearchRoaming.allows()`筛选。该函数用于阻止探索阶段回到初始附近，不能反过来禁止合法返航。新模块直接提供经过既有通道检查的导航目标；只绕过探索区域限制，机身净空、碰撞与实时避障检查继续保留。

### 5.3 各阶段状态与动作

| 状态 | 动作 | 离开条件 |
|---|---|---|
| OBSERVE | 记录路径、接触，搭车交换小元数据 | 有接受的计划且满足返航门槛 |
| RETURN_LOCAL | 前往A/B；无局部点则根点 | 实际接触、到达区域或路由失效 |
| LOCAL_EXCHANGE | 先发末弹确认，再发缺少的快照与候选图 | 本组任务清零，或必须转向C |
| COURIER_TO_C | 已持有本组数据的携图者前往C | 中途实际接触即可进入交换 |
| DELIVERED_HOLD | 已交付组员在安全位置保持，继续收发，不再巡回配送 | 补交缺失数据、协同结束或安全避让 |
| INTERGROUP_EXCHANGE | 只交换双方缺口，不送回来源，不重复融合 | 得到可比较候选，或达到协同截止 |
| SELECT / COMMIT | 同一证据评分，确认候选图与执行者 | 提交条件满足且确认完成 |
| SUBMITTED | 停止任务 | 终态 |
| BYPASS / ABORT / EXPIRED | 不新建返航，或退出已失败任务 | 原版流程与硬兜底接管 |

安全保持不是强行锁死速度指令。保持期间照常读取近障碍信息，必要时让既有避障接管；不得把“交付完成”变成永久禁止移动。

### 5.4 迟到机器与一次配送上限

局部组在自己的预计成员交付完成后立即派出携图者。若未完成，按剩余预算决定最后离开时刻：`local_leave = coord_cutoff - ETA(local_to_C) - exchange_reserve`。本阶段只使用这个绝对时刻，不叠加多轮等待。

到达离开时刻，携图者携已真实收到的数据前往C，明确携带缺口清单。迟到成员知道本epoch的C；若A/B已无人且继续等待无收益，直接前往C。不能追逐过期位置，也不能因为收到旧广播重新跑一圈A→B→A。

每个epoch一架机最多一个返航配送任务；任务内允许A/B→C这两个阶段，不因重复版本回到已完成阶段。真正缺失的新数据可在后续接触时补发，不自动触发第二次远程往返。

## 6. 时间预算：用一个截止时间约束全过程

| 参数 | 首版建议值 | 性质 |
|---|---:|---|
| `RETURN_RATIO` | 0.60 | 用户指定 |
| `BRANCH_STABLE_STEPS` | 40 | 待验证的分支成熟参考值，不是SDK规则 |
| `COORD_CUTOFF_RATIO` | 0.85 | 待验证的协同软截止 |
| `COORD_WALL_RESERVE` | 8 s | 提前退出协同，给提交/兜底留时间 |
| `COMMIT_ACK_STEPS` | 最多2步 | 实际接触后的轻量提交确认预算 |

```python
coord_cutoff = min(int(limit * 0.85), DeadlineSubmission.window_start(limit) - 12)
coord_expired = step >= coord_cutoff or wall_left <= 8.0
```

5400步时软截止为4590步。此值不是要求等到4590；收包和择图完成后马上提交。它也不是新硬交图期限：若全队库存尚未真实确认，不能强制走普通提交。旧硬兜底继续按原条件工作。

所有组内等待、组间等待和选举共享同一个绝对截止，不允许每次消息到达重开24/48步窗口。截止后不再新增绕路和可选拟合，使用已持有的最佳有效候选；满足普通提交条件就提交，否则返回原版处置与硬兜底。

截止事件必须释放新模块的导航所有权和旧普通提交软门控，不能只把状态改成EXPIRED却继续提前return。最后30步的原提交窗口必须可达，即使协同此前失败。

4590只是首版上限建议。Map09旧候选1号4387步才确认末弹，只剩203步，可能根本不够返航。实施前应先用现有轨迹估算ETA；不能靠把截止无限延后掩盖投弹被拖慢的问题。

## 7. 消息与地图数据：什么才算“真正交付”

### 7.1 独立协议，不混用旧缓存的含义

新增命名空间 `red_group_exchange`。小元数据随正常广播搭车，包含计划、库存确认摘要、缺口、收据和角色。大载荷按对方缺口发送，每次消息只带一种大载荷，避免把5份完整地图每帧广播。

首版逻辑对象如下，具体编码沿用SDK已支持的消息类型：

```python
Plan = {epoch, version, root_region, local_regions, member_groups,
        accepted_members, coord_cutoff}
SourceSnapshot = {epoch, owner, version, memory_packet, bearing_bits,
                  inventory_records, digest}
ImageCandidate = {epoch, owner, version, bitmap, source_manifest,
                  snapshot_digest, image_digest}
Receipt = {epoch, receiver, payload_kind, owner, version, digest}
SubmitChoice = {epoch, reference_digest, policy_version,
                image_digest, image_owner, executor, backup, lease_end}
```

epoch取本轮可共享的配置/任务代号；不依赖模拟器真值或不可见随机种子。一个owner/version对应一份不可变内容；摘要覆盖元数据、数组形状/类型和规范化字节。相同版本不同摘要直接拒绝，不允许悄悄覆盖。

### 7.2 快照冻结与版本一致性

每架在首次接管返航时，冻结当时的 `MapMemory.packet()`、方向证据、库存记录，并用**同一份冻结数据**生成自己的候选图。数组必须拷贝；后续live memory和方向证据变化不能改写已标记的版本。

`MapMemory.packet()`包含本机当时已经融合的地图，所以这里的owner表示“该机提交的快照”，不表示每个墙像素的最初作者。收齐5个owner只说明收到5份快照，不说明得到5份独立新增信息。

特别注意 `_render_submission(memory)` 仍可能读取本机当前的 `submission_bearings`。冻结memory却使用live方向证据，会生成版本不一致的图。应以冻结的方向位图构造临时 `SubmissionBearings` 渲染上下文，调用原有render，不更改拟合参数。

重拟合不放在每帧循环：每机冻结后最多生成一次个人候选，尽量按编号错开构建帧；全队最终可选融合图最多额外生成一次。当前帧预算不足时延后候选构建，库存确认和小元数据仍先转发。

### 7.3 收据、缺口与去重

接收方完成摘要/尺寸校验并实际保存载荷后，才对该 `(epoch, kind, owner, version, digest)` 发收据。地图快照和候选位图分别确认。消息发出、距离够近、看到对方广播清单、收到一个普通地图版本号，都不能代替载荷收据。

转发者只有实际持有完整载荷才能宣称可以交付。若清单表明对方已持有同一版本，就不再发送；接收重复载荷只补ACK，不重复合并、不重复计数、不重启任务。目的方等于来源方且来源方已有该版本时不回送。

末弹确认单独优先转发，不能等大图构建完再发。沿用原版库存记录的编号、时间和单调性校验，不使用“预计投完”标记替代实际库存记录。

旧缓存的480步/240步有效期不适合3240冻结、4000多步才见面的组间配送。新增epoch快照在协同期内保持有效；只对新协议这样处理，保留原版普通缓存的TTL，不能全局删除过期检查。

ACK只证明某台机器持有一份数据，不证明其位置可靠或图质量高。接触日志、计划ACK、快照ACK、图像ACK、提交ACK必须区分。

## 8. 怎么选图，以及让谁交图

### 8.1 保留原图，融合只作为额外候选

候选池上限为5张个人冻结图，加1张可选全队融合图。局部组不要提前只保留“暂时得分最高的一张”，否则换一套证据评价时可能已经丢掉真正更好的原图。

全局融合用已校验冻结快照，加上最终评分者当时实际持有的live memory及方向证据，整体再冻结一次，构造临时上下文调用原版渲染。这样能利用返航途中和原广播继续带来的有效信息；只包含评分者实际收到的内容，不能声称包含所有飞机的全部后期信息。它不覆盖个人图，也不自动当作最优图。新增墙多不等于分数高，误画也可能增加。

本方案明确牺牲的是60%以后已空仓飞机的继续远探索时间，以及未能送达的后期信息；仍在投弹的飞机可继续原流程。个人候选以返航接管时的冻结版本为准，最终融合可补入已经实际收到的更新，不因后期变化无限重建候选和重启配送。

Map09图像1700×1100，按packbits每张约233750字节，6张约1.40 MB；这只是位图载荷，不含稀疏证据、消息对象和解码内存。保存编码图，评分时逐张解码复用工作缓冲，避免每帧复制6张全尺寸数组。

### 8.2 所有候选使用同一证据评分

沿用原版 `local_score(bitmap, hits)` 的支持/覆盖Dice思路，不改地图拟合：

1. 最终比较时冻结一份共同证据 `reference_hits`，计算 `reference_digest`。
2. 每张候选都用这份证据计算同一分数，不能甲机用甲机证据、乙机用乙机证据，再直接比较两个数。
3. 排序固定为 `(local_score, candidate_version, -image_owner, image_digest)`；后几项只用于确定性平局，不代表质量收益。
4. 记录评分表、共同证据摘要和候选图摘要。若之后有缺失证据补齐，产生新reference版本重新比较，不能混用旧评分。

`FinalMaps.rank()`主要含快照数量和粗略探索估计，不能作为这里的图质量排名。原 `local_score`也不是官方评分：它使用本机可见证据和下采样邻域，无法识别全队共同定位偏差，更无法与官方真实墙面逐像素核对。因此文档中的“最佳”均指这套统一估计下最佳。

### 8.3 携图者、评分者、执行者分开

组内携图者：在实际持有本组已收到数据的成员中，选到C预计步数最少者；平局按编号。不是默认0号，也不是默认图像原作者。

最终评分者：在已经实际接触的携图者中确定一位临时评分者，发布同一评分表。执行者必须实际持有获胜位图，且自身已空仓、无pending、可执行提交；多位都持有时选预计最早可提交者，平局按编号。

发布 `SubmitChoice` 后最多用2步接触预算确认执行者和备份。执行者在有效租约内唯一；备份只在明确失败/租约到期后接替，不凭“没看到广播”立刻抢交。若时间已触发原硬兜底，则兜底优先，不等待选举消息。

断联且无法收齐信息时，不能保证全局最优或绝对唯一。日志必须说明仅比较了哪些实际持有候选，不能声称“全队最高分已提交”。

## 9. 交图出口与三道旧等待怎么处理

### 9.1 新普通出口的必要条件

```python
can_group_submit = (
    valid_choice_and_executor
    and actually_holds_chosen_bitmap
    and actual_own_inventory == 0
    and pending_drop is None
    and all_team_inventory_confirmed_empty
    and chosen_image_nonempty
    and existing_partial_map_guard_passes
)
```

满足后直接提交，不再依次进入以下旧等待：

- `pre_submit_scan.waiting()`：60%起再等待约180步的扫描窗口；
- `final_maps.waiting()`：旧快照收集窗口；
- `_prefer_own_submission()`：旧图竞价与额外等候。

只在新分组出口绕过，不删除原函数；未启用、预检失败和原版回退路径仍按原规则。地图非空、部分图保护、真实库存确认继续保留。60%前也不开放这个出口。

### 9.2 防止其他提交入口抢先结束

原版不只一个提交位置：`red_hooks.py`有墙钟/步数硬兜底、最后30步窗口和普通提交，`fast_closeout.py`也会直接提交。

新增集中判断 `ordinary_submit_allowed(step, path)`：已接受的分组计划进入协同期后，旧普通出口和快收尾普通提交应受协调状态约束，避免新收包任务尚未完成就被旧竞价结束。硬兜底和最后时限处置不受此软约束。未完成投弹时的快收尾投放与脱离仍可正常执行。

不得用重写 `submit_exploration_map()`、悄悄拒绝调用的方式实现拦截；旧调用者可能无论提交成功与否都设置 `submitted=True`。应在各普通调用者进入提交前明确判断。

### 9.3 最佳候选也必须进入兜底缓存

原 `_submission_image()`在有 `FinalMaps.snapshots` 时提前返回融合图，会跳过普通候选缓存选择。新图选择应在这个分支之前检查“已验证的本epoch最佳候选”，否则选举选中甲图，提交却交出乙图。

将获胜位图、owner/version/digest原子安装为 `group_best_image`，同步 `deadline_submission.image` 和备份；保留原硬兜底触发条件、优先级及可在队伍未完全确认时采取紧急交图的既有行为。后续普通缓存刷新不得用旧图覆盖这个已提交选择。

`_submit_at_deadline()`若更新候选，也必须经同一 `_submission_image()`取到当前已验证选择。不要将新质量分硬塞进旧 `red_map_bid` 数值域；分组选择用独立消息，旧竞价只承担原回退职责。

### 10.1 control调用顺序约束

```python

    return empty_command()

update_lightweight_contacts_and_plan()
run_existing_emergency_closeout_tick()

    return command

# 无新任务所有权时，原信使与原常规流程的顺序保持原样。
# 新任务先只读预检；成功后才进入下面的协同路径。

if intent is not None:
    group.commit_return(intent)

if group.owns_navigation:
    observe_and_refresh_at_existing_cadence()
    retain_required_drop_escape_checks()
    group.receive_and_schedule_missing_payloads()
    if group.try_submit():
        return command
    group.tick_navigation(command)
    apply_existing_local_avoidance(command)
    return command

return original_remaining_control_flow(command)
```

这是顺序约束伪代码，不可直接替换基类调用。实施时抽取原观测/刷新代码为共用方法，保证协同路径不会像旧信使一样因提前return跳过刷新；未启用路径的调用次数和顺序保持原样。

投放动作、在途pending和脱离状态优先于 `commit_return`。已接管的空仓机不会再进入普通投放分支；其他仍带弹机器照旧运行。收发回调和硬兜底不能被重拟合阻塞。

## 13. 分阶段实施与验证顺序

### 阶段一：协议与纯逻辑

### 阶段二：接入控制与已有轨迹离线检查

## 14. 最小实施顺序、回退与交付要求

建议按下面的代码顺序推进，避免一次引入全部变化后无法归因：

1. 修正“无有效计划也清任务”，加入只读预检与审计；保持功能开关关闭时原行为。
2. 加入共享根点、实际接触记录和A/B局部点。先确认能产生可靠计划。
3. 接入60%后历史路径返航、一次任务去重及迟到成员转C。
4. 接入真实载荷收据、冻结候选、按缺口传输；先转发库存确认。
5. 接入统一证据择图、任意持图者提交、新出口与硬兜底缓存一致性。
6. 完成反例和已有轨迹离线预算，之后才做授权的单次Map09测试。

统一开关 `ENABLE_GROUP_EXCHANGE` 控制全部新协议接管和提交门控；关闭时不取消旧信使、不改旧路线、不改变普通提交图选择。可保留无副作用的诊断日志。部署前核对只改预定2个现有文件，新增3个模块，其他文件哈希一致。

正式实施的后续交付应包含候选源码/补丁、配置、反例结果、测试命令、与原版的对照表及可追溯提交。**本次只交设计，不提供冒充已实现的候选ZIP。**

## 15. 给汇报使用的一段话

我们不再要求所有无人机围着0号机返回，也不强求回出生点。探索到总步数60%左右，已经投完弹的飞机沿熟路回到各自分开的地方，先在小组内部交换，再派携图者去双方共同知道的区域交换。地图原图都会保留，融合图只作为备选，最后由实际拿到较好地图的飞机提交。主要卡点不是“多加几个交互点”，而是双方是否约定了同一个地方、消息是否真的收到，以及交互完成后有没有被旧等待规则继续拖住。本次设计分别解决这三件事；是否能提高比赛得分，还要用反例和一次固定种子的对照来证明。
